# 文档规范

## 范围

本规范适用于本项目的 `docs/`。文档组织参考 Firecracker 的项目介绍、设计文档、
使用指南和贡献指南；下列具体约定由本项目采用。
文档使用中文，保留源码标识符、参数和协议字段的原始拼写。

## 文档组织

`README.md` 是阅读入口，简要介绍项目并链接设计、模块和已有接口文档。
`design.md` 说明项目范围、集成关系、内部架构、组件职责、状态与接口边界。
`modules/` 按稳定的职责名称拆分模块说明。

模块文档细分当前实现中的子职责，并标明实际实现位置。
逻辑职责与文件布局可以不同，空占位文件应与实际承载逻辑的文件明确区分。

使用指南说明完成某项操作所需的前提、步骤和预期结果；接口参考说明参数、
结果与错误。已有独立接口文档通过链接复用，避免多处维护同一份参数定义。

## 模块写法

页面先界定范围，再解释内部结构与子模块职责，随后说明输入输出、状态、
生命周期和协作约束。根据模块特征选择章节，不要求所有页面使用相同的章节数量。

每个子职责应回答它处理什么、接收和产出什么、持有什么状态、与谁协作，
并给出可定位的源码路径。无状态转换应明确其存储由哪个组件承担。

正文用段落解释行为和因果关系。表格用于类型映射、状态归属或选项比较。
架构图应标明组件与连接含义，并由正文补充关键流向。

以下结构可用于新增模块文档：

```markdown
# 模块名称

## 范围

说明模块提供的能力及其在项目中的位置。

## 内部结构

### 子模块名称

说明任务、输入输出、状态归属和实际实现位置。

## 接口与生命周期

说明关键调用、状态变化和失败行为。

## 协作边界

说明与其他组件之间的责任交接及现有限制。

## 相关文档

- [文档索引](../README.md)
- [设计总览](../design.md)
```

## 内容规范

陈述当前源码能够支持的行为。版本或提交基线写在设计文档中，
相关源码变化时更新对应描述。
设计提案应明确标注为提案，不能与已实现能力混写。

区分配置与运行状态、请求返回与任务完成、宿主快照与节点事实。
涉及并发时说明锁或订阅的作用域；涉及生命周期时说明创建、退出、停止和移除。
限制与失败行为应具体说明触发条件和结果。

示例应标明前提、参数含义与预期结果。环境地址和路径使用清楚的示例值，
不将某次部署记录写成通用接口要求。未验证的构建或性能结果不能写成已通过。

## Markdown 格式

- 使用 UTF-8、LF 换行和一个文件末尾换行；不保留行尾空白。
- 每页使用一个一级标题，后续标题逐级组织；标题名称表达实际内容。
- 标题、段落、列表、表格和代码块之间保留空行。
- 路径、类型、函数、字段和命令名使用行内代码。
- 代码块标明语言，例如 `rust`、`bash`、`json`、`markdown` 或 `mermaid`。
- 正文按句或可读宽度换行；代码、链接和表格单元格不做破坏语义的硬拆分。
- 仓库内使用相对链接，链接文字说明目标内容；移动文件时同步更新引用。
- 文档目录保持文件名稳定，新页面加入索引或其所属模块的相关文档。

## 变更与检查

接口、默认值、状态和模块边界变化时，同步更新相应文档。
审阅时核对正文与源码的一致性，检查链接目标、标题锚点、代码块、表格和空白格式。
文档改动的检查结果与代码构建结果分别记录。
